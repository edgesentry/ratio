## 主張（一文）

> 物理ドメインは、現場で導出したガバナンス付き・オントロジー裏付けの **共有可能プロダクト** の Pull 提供者として ODS に参加する。**既定の外向き経路はそれらのプロダクトであり、観測の生データではない。**

これは **Ratio の運用定義**であり、ODS-RAM からの引用ではない。

## 利用者の目的 · ODS で何をするか · 何を得たいか

三点を分けて固定する。「意味だけ伝えて ODS は使わない」ではない。

### 1. 利用者の目的（ビジネス上やりたいこと）

| 利用者 | 目的 |
|--------|------|
| **現場ドメインオーナー**（工場・船舶等） | 生データ／ノウハウを外に出さず、パートナーや上位システムと現場の状態を共有・連携したい |
| **ODS 消費者／Agentic AI／パートナー** | 許可された範囲で、現場の判断材料を発見し Pull して業務・推論に使いたい |
| **標準実装者**（W3C／ODS） | 独自方言ではなく、公開標準と公式スタックで上記をつなぎたい |

### 2. 本プロダクト（Ratio）が ODS と何をしたいか

| すること | しないこと |
|----------|------------|
| 現場で **共有可能プロダクト**（結果＋オントロジー文脈＋利用条件）を作り、**公式 ODS スタック**で登録／発見／Pull 提供する | 生データを ODS で主に提供する |
| DPQM の関心（データと文脈の対）を **現場発生点で具体化**する | ODP／Middleware を自前再実装する |
| W3C（JSON-LD／SHACL／WoT／DID・ODRL 等）で製品の意味と検証を載せる | スコアのみの非標準 Blob を「ODS 参加」と呼ぶ |

### 3. それで何を得たいか（成果）

| 側 | 得たい成果 |
|----|------------|
| **現場** | 秘匿・帯域不足・通信の途切れがあっても **ODS 参加者（提供者）になれる** |
| **外の利用者** | 生データなしでも、**どの機器・どんな文脈・何が許されるか**が分かる製品を Pull し、エージェント／業務が動ける |
| **両者** | データレイクのミラーでもブラックボックス・スコアでもない、**統治された相互運用**（透明性＋制御） |

一文:

> 利用者は「生データを守った現場連携」と「外からの正当な利用」を望む。Ratio は ODS に **共有可能プロダクトだけ**を載せて参加させ、その結果として現場は参加資格を、外は使える判断材料を得る。

### 4. ODS 側のメリット

「ODS 側」＝データスペース運営・他参加者・Agentic AI が依拠する基盤の側。

| メリット | 内容 |
|----------|------|
| **実データの供給口が増える** | 工場・船舶など、データレイクに出せなかった OT ドメインが Pull 可能な提供者として参加できる |
| **ダーク／リアルデータの品質** | スコアだけでなく、オントロジー付き・検証可能な製品が流れる（GIGO を減らせる） |
| **DPQM が現場で実体化する** | データと文脈の対が発生点で分かれ、中央に生データを集めてから意味付けする歪みが減る |
| **統治と信頼** | 利用条件付きで渡るため、用途外・生データの無断持ち出しを前提にしない連携が設計できる |
| **標準の射程が現場まで届く** | ODP／SDK が IT ノードだけで終わらず、物理ドメインまで公式スタックが効く |

ODS にとっては、**参加ノードの業種・地理カバレッジ**と、**Context 付き実データの供給**が増えることが主益。

### 5. Ratio だけだと足りない部分

Ratio は「現場で製品を作り、公式スタックへ渡す糊」まで。**ODS 参加者としての一式の代替ではない。**  
不足を **公式 ODS が既にサポートするもの**と、**公式の外（ドメイン／アプリ／合意）で埋めるもの**に分ける。

#### 5.1 公式 ODS でサポート済み（Ratio は再利用・接続する）

| 不足（Ratio が持たない） | 要件 | 公式の置き場 |
|--------------------------|------|----------------|
| **L3 アイデンティティ**（トークン、事業者登録等） | O1 | L3 Identity Component、`SDK-docker-compose`、`SDK-client-library-python` |
| **L2 転送・取引** | O4 | L2 Web API Transfer（`L2-dp-webapi`） |
| **カタログ／Discovery・メタデータ** | O2–O3 | L4 Discovery／Metadata 系（Discovery Service、Finder 等） |
| **利用制御・契約まわりの基盤** | O8 | ODS-RAM パースペクティブ、ODP 補完（Heuristic Contracting 等）、L3-PAP 等 |
| **信頼・品質アセスメント手順** | O7 | ODP L1 assessment プロトコル群 |
| **運用・監視・ロギング** | O9–O10 | Middleware 共通機能、logging サービス、開発者／利用者ガイドのオンボーディング |

PoC の `ratio-serve` は上記の **代替ではない**（L2 上流 industry API の仮置き）。本番では公式 Compose／L2／L3／L4 に接続する。手順: [`ODS_HANDOFF.ja.md`](ODS_HANDOFF.ja.md)。

#### 5.2 公式 ODS だけでは足りない／範囲外（他者が担う）

| 不足 | なぜ公式だけでは埋まらないか | 誰が埋めるか |
|------|------------------------------|--------------|
| **現場での製品導出・生データ／プロダクト分離** | ODS は分散データ管理・Context 層であり、OT エッジの導出エンジンそのものではない | **Ratio**（本プロダクトの役割） |
| **消費者アプリ／Agentic AI 本体** | Pull した製品を業務・推論に使うのは利用者アプリケーション | パートナーアプリ、上位 AI（例: 利用側エージェント） |
| **ドメインオントロジ・語彙合意** | 標準は枠を出すが、業種固有語彙の合意はドメイン所有者間の仕事 | 業種コンソーシアム、SAMM／SDK for semantics を使った定義作業 |
| **具体セル／船／ベンダー接続** | WoT TD 等の枠はあるが、実機 I/F・SI は現場ごと | SI、既存 IIoT／WoT ゲートウェイ、ドメインオーナー |
| **法的認証・安全責任（ハード RT 制御等）** | データスペース仕様の外（または別制度） | 規制・認証機関、制御ベンダー、ドメインオーナー |

**読み分け:** 「足りない」の多くは **公式をまだ繋いでいない**だけ（§5.1）。Ratio を増やして埋める対象は主に現場導出であり、L2／L3／L4 を Ratio が再実装する話ではない。

**スコープの正本（公式 ODS／Ratio／スコープ外と担当）:** [`SCOPE.ja.md`](SCOPE.ja.md)

準拠 ID（O1–O10）の詳細: [`ODS_COMPLIANCE.ja.md`](ODS_COMPLIANCE.ja.md)。

| 枠 | 内容 |
|----|------|

一文:

> 生データを出せない物理ドメインが、**共有可能プロダクト**だけを Pull させて ODS に参加できるようにする。エッジ AI・GW・IT 側 ODS ノードに似るが、違いは **生データ非egress × 公式スタック参加**。制御や ODP は作り直さず、プロダクト・パイプラインにスコープを限る。

## 定義

### 共有可能プロダクト（shareable product）とは

**共有可能プロダクト**（別名: 意味付きプロダクト／meaning-bearing product）は、既定でドメインから ODS へ出る **唯一の対象**。

生データファイルではない。消費側が解釈し行動できる構造化パッケージである:

| 必須 | 意味 | 例 |
|------|------|-----|
| **結果** | 観測または判断の内容 | `vibration_abnormal`、confidence `0.96` |
| **意味** | 機械可読な文脈: *どの*ものか、*どんな*オントロジー／特性か、*何を根拠に* | WoT／DID デバイス ID；JSON-LD `@context`；physicalContext（RPM、℃）；語彙へのリンク |
| **利用条件** | 誰が何目的で使えるか | `policyRef`／ODRL 系参照 |
| **作成の記録／品質**（主張する場合） | Pull するに足る信頼の理由 | タイムスタンプ、SHACL レポート参照、モデル／タスク ID |

**意味付き**とは: パートナーや Agentic AI が、生データの波形／画像を開かずに「これは何についてのものか」に答えられること。識別子・語彙・文脈が結果と **一緒に**運ばれる（DPQM 整合: データ関心とオントロジー／文脈関心の対）。

| 共有可能プロダクトである | ではない |
|--------------------------|----------|
| JSON-LD（等）の判断＋`@context`＋デバイス ID＋policyRef | 語彙なしの `{ "anomaly": 0.98 }` |
| 主張する SHACL 形状に対する検証済み | 未文書化のスコア CSV |
| ODS 上で発見・提供できる | 既定で同じ Pull 経路に乗る `.bin`／動画 |
| ドメイン **内**の `rawDataPointer` を持てる | 既定で生データをダウンロードさせる公開 URL |

本文書の正式語: **共有可能プロダクト**（英語併記時は **shareable product**）。不透明スコアとの対比でのみ「意味付き」を使う。

### 用語

| 用語 | ここでの意味 |
|------|----------------|
| **物理ドメイン** | 観測を **生成**し、ローカル推論しうる OT／現場のドメインオーナー（工場セル・船舶・ロボットライン）。コーポレート・データレイク単体ではない。 |
| **生データ** | 物理観測や中間成果のペイロードバイト: 波形、画像、動画、高頻度サンプル、独自工程ログ、特徴量ブロブ等。ファイル／DuckDB／LanceDB 等にドメイン保管。 |
| **共有可能プロダクト** | 上記。Pull 可能な **結果＋意味＋利用条件**（＋作成の記録）。**生データではない**。DPQM の Data Product＋Ontology Product *関心*を現場で具体化したもの。 |
| **出荷（shipping）** | データスペース参加の既定経路として、生データ（ペイロードバイト）を **ドメイン境界の外**へコピー／配信すること。 |
| **ODS への参加** | **公式 ODS スタック**（ODP／Middleware／SDK）によるメンバーシップとプロダクト提供。「工場をクラウドにアップロード」ではない。 |

### 「ODS に参加する」の具体

公式 ODS スタック経由（Ratio は ODP を **再実装しない**）:

1. **ノードになる** — ドメイン／ノードの認証済みアイデンティティ
2. **プロダクトを公開／登録** — 何があるか・意味・利用条件が発見可能
3. **Pull で提供** — 許可された内容を要求に応じて配信（中央データレイクへの全 Push ではない）
4. **利用を統治** — 誰が何を何目的で（ポリシー／ODRL 系、適用可能な範囲）

規範マッピング（O1–O6 等）: [`ODS_COMPLIANCE.ja.md`](ODS_COMPLIANCE.ja.md)

### 「生データを出さない」の具体的な意味として

```
[デバイス] → 生データ → ローカル保管（ドメイン内）
                    ↓
             導出／推論／検証
                    ↓
             共有可能プロダクト（文脈＋結果＋作成の記録＋policyRef
                               ＋任意のローカル生データポインタ）
                    ↓
             ODS（共有可能プロダクトのみ発見＋Pull）
```

| 主張すること | 主張しないこと |
|--------------|----------------|
| 生データは既定でデータスペース参加の対象にならない | 生データは現場で処理しない（する；それが要点） |
| 消費者は行動／判断に足る意味付きプロダクトを得る | 常にビット同一のセンサダンプを得る |
| `rawDataPointer` は **ドメイン内**にありうる | そのポインタは公開ダウンロード URL |
| **別途明示ポリシー**の下で、統治された生データのエクスポートを後から許すことはありうる | 「生データを出さない」＝将来の二者契約をすべて禁止 |

### 最小例

- **生データ（ローカルのみ）:** `raw_wave_20260816_001.bin`
- **共有可能プロダクト（ODS-Pull 可）:** デバイス *D* が時刻 *T* に `vibration_abnormal` @ 0.96、オントロジー *O*、SHACL *R*、ポリシー `internal-only-rawdata`；生データは `local://…`
- **参加:** パートナーは ODP でプロダクトを Pull；別許可がなければ `.bin` は届かない

### 失敗モード（主張の外）

- カメラ／振動ストリームを「ODS のため」中央データレイクへミラー
- オントロジー／文脈なしの不透明スコア（`anomaly: 0.98`）だけ公開
- ポリシー分離なしで、生データファイルをメタと同じ Pull 経路に載せる

## 構築方針

**既定: OSS と公開標準／公式 ODS SDK。**  
**作るのは** 導出・検証・生データと共有可能プロダクトの分離、そして ODS への引き渡しの糊だけ。

| 優先して再利用 | Ratio として構築 |
|----------------|------------------|
| Oxigraph、DuckDB、LanceDB、SQLite、Arrow | オーケストレーション: 取込 → 導出／検証 → 分離 → ODS への引き渡し |
| W3C WoT TD、JSON-LD／RDF、SHACL、DID／VC、ODRL | 共有可能プロダクト形状＋Arrow を使う Memory Broker の契約 |
| IPA ODS Middleware／SDK、ODP | 引き渡しの境界で R1–R4 を満たすパッケージング |
| ONNX Runtime／一般的推論ランタイム | ドメイン PoC 配線（デバイス系統、SHACL 形状） |

## 主張が当てはまるとき（需要条件）

次の **3つすべて**が成り立つときだけ Ratio が正当化される:

1. 既定で生データを **出してはならない**（秘匿／帯域／ポリシー）、**かつ**
2. セル／船の外の誰かが **意味**を必要とする（ローカルダッシュボードだけでは足りない）、**かつ**
3. **ODS Pull 参加**が欲しい（単発のファイル受け渡しではない）

### 具体的なシーン（3つが同時に立つ）

| 条件 | 工場（K1: セルロボットの振動） | 船上（S1/S2: 機関シャフト振動） |
|------|--------------------------------|--------------------------------|
| **1. 生データを出さない** | 溶接／組立セルの振動波形はノウハウと帯域の理由で工場外に出せない。カメラ映像も同様。 | 高頻度のシャフト振動は帯域が細く、通信も途切れがちなので陸へ送れない。船体 CCTV も船上に残す。 |
| **2. 外が意味を欲する** | パートナー OEM や品質エージェントは「どのロボットが、どの工程で `vibration_abnormal` か」が欲しい。セル横の HMI スコアだけでは取引先は動けない。 | 陸上のフリート運用や保険／ヤードは「この船の機関が異常か、いつ、どのセンサか」が欲しい。波形そのものではない。 |
| **3. ODS で Pull する** | 取引先がデータスペース上でプロダクトを発見し Pull したい。USB やメールで JSON を渡すだけでは、参加・利用条件・発見が乗らない。 | 通信が戻ったとき、陸上／パートナーが ODS 経由で同じ書式のプロダクトを Pull したい。衛星に生データを上げて IT 側で ODS する、ではない。 |

三つが揃うと: 波形は現場に残り、外には JSON-LD の判断＋文脈＋利用条件だけが届く（工場はオンライン Pull、船上は必要ならキューしてから Pull）。

いずれか欠ける場合: クラウド ODS ノード、素のエッジ AI、非 ODS 連携で足りる。Ratio は任意。

| 欠け | 足りるもの（例） |
|------|------------------|
| 1 がない（生データを出してよい） | データレイクへ上げ、IT 側の ODS ノードで足りる |
| 2 がない（外は意味を要しない） | セル／船上のローカル HMI や単体エッジ AI で足りる |
| 3 がない（ODS 参加が不要） | MQTT ダッシュボードや、都度のファイル受け渡しで足りる |

### 主張を動機づける課題

| # | 課題 | 主張との関係 |
|---|------|----------------|
| E3 | 帯域 vs 生データの量 | 生データの出荷はしばしば非現実 |
| E4 | 生データとノウハウの秘匿 | 生データをデータスペースの対象にしてはならない |
| E8 | セマンティック・ギャップ | 共有可能プロダクトが意味を運ぶ必要がある |
| E2 | 帯域が細い／通信が途切れがち | 外に出せるのは意味だけ、が現実的 |
| E9 | ノードの信頼 | Pull 可能な対象へのアイデンティティ＋ポリシー |

Ratio のスコープ外（この主張では解かない）: ハードリアルタイム制御（E1）、万能 OT マルチプロトコル GW 製品、アプライアンス SKU、法的認証、ODP 再実装やストアのフォーク。

### スコープ内（Ratio が解くこと）

| 解くこと | 方法（再利用優先） |
|----------|-------------------|
| 生データをローカルに留め、**共有可能プロダクト**を Pull 可能に | ローカルストア＋JSON-LD パッケージ；公開／提供は ODS SDK |
| 観測／推論に **文脈**を付与 | Oxigraph＋JSON-LD／RDF；ドメイン形状は設定 |
| 共有（または行動）前に **検証** | Oxigraph SHACL；ポリシー／資格は SQLite |
| 制約下の egress | ポインタ＋ポリシー；新規トランスポートは作らない |
| 境界での薄い WoT TD | TD を消費；フィールドバスドライバは全部作り直さない |

---

## EdgeSentry 内の役割

- **EdgeSentry** — 現場ガバナンス＆セキュリティの親ブランド  
- **Ratio** — 現場で判断の根拠（結果＋意味＋利用条件）を共有可能プロダクトにし、公式 ODS へ引き渡す構成レイヤ

---

## なぜこの OSS スタックか

| コンポーネント（OSS） | 主張における役割 | 再発明しない理由 |
|----------------------|----------------|------------------|
| **Rust** | 薄い構成ランタイム | 自社はシェルのみ |
| **Oxigraph** | 意味＋SHACL 検証 | W3C ネイティブエンジン |
| **DuckDB／LanceDB／ファイル** | 生データ／成果物のローカル保管 | ストレージは解決済み |
| **SQLite** | ノード状態、DID／VC、ポリシー記録 | 枯れた ACID |
| **Apache Arrow** | Python／SLM への橋 | 標準メモリ形式。それを使う Memory Broker の役割は Ratio |
| **IPA ODS SDK** | 参加（O1–O6） | 公式経路 |

**単一原則:** 生データと重い計算はドメイン内；**ODS に乗るのは共有可能プロダクト。**

---

## 主張が崩れる別案

| パターン | 失敗理由 |
|----------|----------|
| クラウド集約 AI／データレイクのミラー | 既定で生データ（相当）を出荷 |
| 単体エッジ AI のスコアのみ | ODS 消費者向けの発見可能な意味がない |
| 私的 API に「ODS」ラベル | 公式スタック参加（O6）ではない |
| 全部自前 | ODP／W3C から乖離；Middleware の重複 |

## 成功の定義

**短期（PoC）:**

- 1デバイス系統を入れ、意味付き JSON-LD の共有可能プロダクトを出す
- 生データはローカル；プロダクトは ODS SDK で発見／提供可能
- 陸上／パートナーの Pull エージェント（`ratio-pull`）は意味だけ読む — 生データなし
- 一覧: 各能力 → OSS／SDK または Ratio 所有（[`POC.ja.md` reuse vs build](POC.ja.md#reuse-vs-build両分野)）

**中期:**

- 主張する場合、公開／行動前に SHACL
- 引き渡しのときにポリシー参照を執行可能
- Python／SLM 向け Arrow I/F の安定
- ODP やストアの並行再発明なし
